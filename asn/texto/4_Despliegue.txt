Retos en despliegue de aplicaciones
en la nube
● Diferentes servicios y sus características según el proveedor
● Diferentes interfaces administrativas en un mismo proveedor: Web, CLI,
  Api REST
● Entornos heterogéneos (nubes híbridas), servicios en redes de empresa...
  (on-premises)
● Dificultad para realizar, replicar, supervisar despliegues...¿automatización?
Soluciones:
 ● (clásica) Aprovisionamiento mediante scripts cli/api rest
 ● (actual) Sistemas de orquestación para control de despliegues
    ○ Codificación de las características del despliegue de sistemas
       distribuidos. Infraestructura as a Code, IaaC

¿Cómo organizar el despliegue de
una aplicación en la nube?
● Clasificar componentes atendiendo a su funcionalidad y grado de
  interrelación, e.g. frontales web, servidores de aplicaciones, sistemas de
  almacenamiento, etc.
● Organización de la red: segmentación (HA y seguridad)
   ○ Regiones geográficas, e.g. GCP us-central1 en Council Bluffs, Iowa
   ○ Zonas en la región, e.g. us-central1-a, us-central1-b, …
   ○ Subredes IP públicas y privadas
● Establecer controles de acceso en la red:
   ○ Acceso público desde Internet (DMZ)
   ○ Acceso entre componentes
   ○ Acceso de administración

Controles de red en la nube
● Objetivos:
  ○ Contener/Dificultar el acceso no autorizado a los componentes de la
      aplicación
  ○ Facilitar la detección de problemas y posibles ataques
  ○ Complementar las medidas de seguridad implantadas en la aplicación
● Diferencias con redes privadas:
  ○ Perímetro de red (DMZ) no definido, e.g. múltiples zonas geográficas,
      proveedores, servicios SaaS, …
  ○ Rápido aprovisionamiento y configuración homogénea, e.g. VPC, ACL,
      Security Groups, …
  ○ Diferencias y limitaciones según el tipo de servicio: IaaS, PaaS, CaaS,
      FaaS

Métodos de segmentación de red en la nube
Virtual Private Clouds (VPC)
 ●    Permiten organizar y aislar recursos definiendo subredes privadas independientes
       ○ 10.x.x.x, 192.168.x.x, 172.16-31.x.x

      orquestación.

           Proxys-Gateways
 ●    Uso de listas de control de acceso para determinar tráfico entrante/saliente

     Kubernetes, K8s
Definición:
"An open source system for automating deployment, scaling, and
management of containerized applications across clusters of hosts"
 Historia
  ● 2014 Google hace open-source su proyecto Borg de gestión de contenedores (usado en
      Gmail o Google Search)
  ● Cedido a la Cloud Native Computing Foundation, CNCF

  ●    Actualmente es ofrecido por los grandes proveedores en la nube: Amazon EKS, Google
       GKE, Microsoft AKS…

 Características Generales:
  ● Gestión de cambios para aplicaciones en contenedores: Despliegues (rollouts) y
     recuperación de estados previos (rollback) de recursos distribuidos
  ● Independiente de proveedores, lenguajes/frameworks de desarrollo, herramientas de
     monitorización, registro y cualquier servicio adicional
13    Aplicaciones Seguras en la Nube. jrbalsas@ujaen.es. http://tiny.cc/asnuja. 2026




Características k8s
● Reubicación automática de contenedores en un clúster de equipos
  anfitriones (nodos) según sus necesidades de recursos
● Auto-escalado de contenedores (pods) horizontal (HPA) y vertical (VPA)
● Auto-escalado horizontal de nodos del Cluster, es decir, VMs
● Servicios integrados habituales en aplicaciones distribuidas
   ○ Descubrimiento de servicios y balanceo de carga
   ○ Gestión de la configuración y secretos
   ○ Gestión de almacenamiento virtual
   ○ Control de acceso a recursos
   ○ Planificación de procesos por lotes
● Admite extensión de funcionalidades mediante plug-ins

Componentes principales k8s
 ●    Nodos, máquinas físicas o virtuales sobre las que se ejecutan los componentes
 ●    Nodo/s Máster, control del clúster, gestión de la carga de trabajo y comunicación
      entre elementos del sistema
       ○    etcd, repositorio clave-valor con información de configuración de estado del clúster
       ○    Controller manager, gestor de funcionamiento de despliegues
       ○    API server, para comunicación y gestión del cluster
       ○    cAdvisor, monitorización de recursos y rendimiento
 ●    Nodos esclavos, ejecutan los contenedores
       ○    Container runtime, encargado de la ejecución del tipo de contenedores escogido,
            e.g. containerd, cri-o, docker engine,...
       ○    Kubelet, control del estado de ejecución de los contendores
       ○    Kube-proxy, con funciones de proxy y balanceo de carga para permitir acceso a los
            contenedores
       ○    Otros elementos: interfaz web (dashboard), autodescubrimiento (DNS),
            monitorización de métricas, e.g. cpu, memoria, disco, red… y registro, logging

Conceptos Kubernetes (I)
●     Pod, agrupación de 1 o varios (sidecars)
      contenedores en una misma ubicación
      (nodo) que comparten recursos, e.g. ip,
      volumen, …
        ○ Unidad básica de planificación
        ○ No conservan el estado, descartables
        ○ Los contenedores en un mismo pod
           se comunican a través de localhost
●     Volúmenes, Permiten a los contenedores
      acceder a recursos externos: discos,
      ficheros, variables de estado, secretos,...
      independientes de su ciclo de vida

Ejemplos de comandos básicos

 POD puerto del contenedor
 $ kubectl create deployment --image=traefik/whoami wwwserver

 Publicar el puerto del pod en el Nodo (Creando un servicio)
 $ kubectl expose deployment wwwserver --port=80 --type=NodePort

 Consultar elementos creados:
 $ kubectl describe service wwwserver
 $ kubectl get pods -o wide      #nodes, deployments, services… usar all para listar todos
 $ kubectl logs svc/wwwserver    #consultar logs
 $ kubectl exec wwwserver-6d4977554c-8glrd -it -- bash # ejecutar comandos en pod

 Consultar servicios publicados en cluster (internos o externos)
 $ kubectl get services

 Parar recursos: Servicio, Deployment y Pod
 $ kubectl delete service,deployment wwwserver

Escalado y auto-escalado horizontal
 ●     Los controladores de escalado se encargan de mantener el estado de los PODS
 ●     Las réplicas de pods en un deployment pueden ajustarse de dos formas:

Escalado manual
Monitorizar réplicas (con k9s o kubectl en ventana aparte)
(shell 1) $ kubectl get pods -w --selector app=phpwebapp # ojo, no parar comando
(shell 2) $ kubectl scale --replicas=3 deployment phpwebapp


Auto-escalado (horizontal)
 ● Basado en utilización de cpu o incluso métricas personalizadas
 ● Creación de objetos específicos HorizontalPodAutoscales (hpa)

$ kubectl autoscale deployment phpwebapp --min=2 --max=5 --cpu-percent=80

     Infrastructure as a Code, en K8s
Motivación: definir la infraestructura de una aplicación en la nube mediante ficheros que definen
sus componentes, características e interacciones
Ventajas:
 ●   Replicación automática de infraestructuras complejas sin necesidad de procesos manuales
 ●   Control de cambios mediante sistemas de control de versiones, e.g. git
 ●   Análisis estático de características de infraestructura, e.g. aspectos de seguridad
IaaC en K8s
  ● Definición y estado de objetos mediante objetos JSON
      ○ Edición más simple en formato jerárquico YAML
  ● Gestión de objetos mediante ficheros
      ○ Imperativa
            ■   $ kubectl create/replace/delete -f fichero_dir/ [-R]
            ■   $ kubectl get tipo objeto -o yml, # obtener estado actual del objeto
            ■   $ kubectl edit tipo objeto # Editar y aplicar nuevo estado
      ○    Declarativa
            ■ Enfoque preferido
            ■ K8s adapta el estado del objeto para reflejar una nueva configuración
            ■   $ kubectl apply -f fichero_dir/

Gestión de ciclo de vida de Pods
Los controladores definen ciclo de vida de los pods según sus características:
 ●   Deployments, gestionan el número y tipo de instancias activas (ReplicasSet)
     además de permitir recuperación de un estado previo (rollback)
            ■   Estrategias de despliegue:
                  ●   Recreate, destruir las instancias activas y lanzar las nuevas
                  ●   RollingUpdate, se van apagando progresivamente las instancias
                      actuales y se van lanzando las nuevas, e.g. nueva versión de la app
 ●   StatefulSets, control de pods con identidad de red permanente y
     activación/desactivación ordenada, e.g. databases
 ●   DaemonSets, control de pods con réplica en cada nodo, e.g. monitorización de
     nodos...
 ●   Job, CronJob, Ejecución de tareas por lotes o programadas

●      ClusterIP ( por defecto), accesible en IP interna exclusivamente dentro del
       clúster o sin ip (None)
●      NodePort, igual que ClusterIP para acceso dentro del clúster, pero también
       permite acceso externo en otro puerto vinculado a la ip externa de los nodos.
        ○ Restricciones: la ip de los nodos puede variar, el puerto externo está en el
            rango 30000-32767
●      LoadBalancer,
        ○ Expone el servicio a través de un balanceador de carga del proveedor en
            una ip y puertos fijos para redes externas
        ○ Crea automáticamente un ClusterIP y un NodePort. Requiere costes
            adicionales por servicio (ip estática por servicio)
●      ExternalName, vincula el servicio a una máquina externa al cluster para
       acceso unificado desde todos los pods del cluster

 ●         Servicio de tipo LoadBalancer
            ○ ClusterIP que delega en un balanceador externo al cluster

            ○ Enrutador de peticiones HTTP(L7) externas a servicios internos del clúster
            ○ Suele recibir peticiones de un LoadBalancer externo
            ○ Requiere un software específico (Ingress controller) que se encargue de su gestión, e.g.
               nginx, haproxy, traefik, etc.
 ●         Recursos Gateway API
            ○ Evolución de los Ingress que combina otros tipos de enrutado, e.g. L7 y L4
            ○ Admite y unifica configuraciones avanzadas de enrutamiento y funcionalidades adicionales de
               balanceo que previamente se debían configurar de forma independiente
            ○ Actualmente está en proceso de implantación (debe habilitarse expresamente) y está siendo
               adaptado por los diferentes desarrolladores a sus productos, e.g. traefik

 Despliegue de aplicaciones en GKE
  ●     Realizar operaciones habituales con kubectl imperativas o declarativas… Algunos
        ejemplos simples:
 $ kubectl create deployment --image traefik/whoami --port 80 testapp

  ●     Las imágenes propias publicarlas en un registro, e.g. google cloud registry, gcr.io,
        docker-hub, ...
  ●     Publicar servicio en Internet y obtener ip pública (ojo, se activará GLBC $$$ )
 $ kubectl expose deployment testapp --target-port=80 --port 80 --type=LoadBalancer
 $ kubectl get service testapp --watch #esperar 2' a 5' hasta que muestre una ip externa de acceso

  ●     Nota: Si no usáramos el balanceador, en GKE los servicios NodePort no son accesibles desde
        el exterior por defecto:
          ○   Los nodos GKE tienen ip en una VPC privada
          ○   Es necesario crear reglas específicas en firewall para darle acceso
          ○   No obstante se podría acceder para pruebas desde host local creando un proxy temporal
 $ kubectl port-forward service/testapp 8080:80                                 #acceder a app en http://localhost:8080
