Severidad de las amenazas
● Motivación: En ocasiones interesa conocer las características de la amenaza y ser capaz de
     priorizarlas para atenderlas adecuadamente
●    Common Vulnerability Scoring System (CVSS v.3): https://www.first.org/cvss/
     ○     Proporciona un valor numérico Score (1-10) con la severidad de la amenaza
     ○     La calificación base se obtiene a partir de:
            ■    Indicadores del tipo de explotación (40%):
                  ●    Vector de ataque (AV): N network, A adjacent network, L local, P physical
                  ●    Complejidad del ataque (AC): L low, H high            Calculadora on-line:
                  ●    Privilegios requeridos (PR): N no, L low, H high      https://nvd.nist.gov/vuln-metrics/cv
                  ●    Interacción de un usuario (UI): N no, R required      ss/v3-calculator
            ■    Indicadores del posible impacto (60%)
                  ●    Alcance (Scope, S): C Changed (otros componentes), U Unchanged (solo al componente afectado)
                  ●    Confidencialidad (C), Integridad (I), Disponibilidad (A): H High, L Low, N no aplica
     ○     La calificación puede variar dependiendo de la evolución temporal de la amenaza y de su posible
           impacto en cada organización
     ○     Ejemplo:
            ■ Java Struts, CVE-2017-5638 , Log4Shell CVE-2021-44228
               ● CVE-2021-44228 CVSS Score: 10.0 Vector: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H

A01.- Insuficiente control de acceso
Proceso: Usuarios, identificados o no, pueden manipular (consciente o        OWASP 2021                A01
inconscientemente) una petición HTTP: URL, parámetros, encabezados, cookies… CWEs                        40
para acceder a recursos que no les corresponden                              Explotabilidad              7,0
 ●   Ejemplo: http://host/app/recurso/1 (¿y si cambiamos a mano el id?)                 Impacto          3,8

Posibles contramedidas
      ●   Políticas de control de acceso sobre URLs, e.g. RBAC
      ●   Verificar privilegios del usuario para acceder a cualquier recurso específico. Denegar por defecto
      ●   Evitar uso de llaves primarias en urls: utilizar referencias temporales en urls que tengan
          asociadas las llaves primarias en contexto de sesión,
            ○ e.g. http://host/app/recurso/1 hace referencia al recurso con llave primaria 345
      ● Procesar sólo la información esperada y de fuentes confiables en una petición, DTOs, ficheros,
          opciones, prevención CSRF o uso CORS
            ○ e.g. http://host/app/user/edit/1 → POST nombre=pepe&isadmin=true
      ● Utilizar mecanismos del framework para controlar el acceso en diferentes capas: presentación,
          control, servicio...
      ● Restringir acceso a metadatos, e.g. listado de carpetas públicas, carpetas .git, etc.
      ● Registrar abusos, limitar intentos no válidos

        ○ OJO, si hay vulnerabilidades XSS, las medidas anti CSRF pueden saltarse fácilmente (las

¿Cómo defenderse frente a Cross-Site Request
Forgery (CSRF)
● Posibles contramedidas CWE-352
      ○   Uso de un token no predecible y de un solo uso (nonce) en peticiones para
          verificar en servidor la legitimidad de una petición. Especialmente en las que
          impliquen cambios (C-UD) en el servidor
      ○   Uso de las facilidades anti CSRF de frameworks de desarrollo y servidores
      ○   Doble autenticación para operaciones críticas, captchas, doble factor
      ○   Comprobar encabezados Origin, Referer y Host de peticiones en servidor
      ○   Uso de atributo SameSite en cookies
      ○   APIs REST/SOAP que limiten peticiones CORS solo desde sitios válidos
      ○   Normas de uso para usuarios: evitar pulsar en enlaces dudosos, cerrar
          sesiones de aplicaciones o evitar accesos simultáneos (pestañas) a sitios
          diferentes…

 Prevención CSRF con tokens
 ●   Método habitual: token sincronizado entre cliente y servidor (contexto de sesión)
      ○ Los frameworks de desarrollo permiten gestionarlo automáticamente
 ●   El servidor rechaza la petición si el token enviado no coincide con el esperado

 ●   Funcionamiento:
      ○ token único por sesión con suficiente longitud obtenido de un generador aleatorio
          criptográficamente seguro
      ○ En peticiones POST, añadido como campo oculto
      ○ En GET, añadir como parámetro, generalmente en operaciones que no implican cambio de estado
          en el sistema
            ■ Si se envían en la URL, evitar que puedan ser capturados (e.g. Referer a sitios externos) o
                renovar en cada petición
 ●   Ejemplo

<form name="form" action="changeUserData" method="POST">
     <input type="hidden" name="_csrf" value="4c05-98a4-b35851daecc1"/>
     <input type="text" name="email" value="" />
     <input type="submit" id="btn" value="Send" />
</form>

 Otros métodos de protección CSRF
  ●    Sin estado en servidor, el servidor "no recuerda" el token que va a recibir
        ○ Doble token:
              ■ Enviar el mismo token en petición y como cookie.
              ■ Una petición CSRF enviaría la cookie pero no el token
        ○ Token cifrado en servidor (recomendado)
              ■ cifrado(ID_sesión+tstamp+nonce)
              ■ solo el servidor puede descifrar el token
  ●    Evitar CSRF en API, para peticiones AJAX
        ○ Comprobar encabezado sec-fetch-site.Valores: same-origin, same-site, cross-site
        ○ Enviar encabezado privado, e.g. X-CSRF-Token: RANDOM-TOKEN-VALUE
              ■ Solo puede añadirse desde JS y la petición debe ser al mismo origen u origen
                 permitido (CORS)
  ●    Activar propiedad SameSite en cookie de sesión
           ○La cookie solo se envía desde contenidos del sitio original (modo Strict)
           ○También en peticiones seguras que no cambian estado como GET (modo Lax), por defecto desde Chrome
            76, Firefox 70 (jun 2020)
   ●   Protecciones específicas del navegador, e.g. 2024 no se admiten cookies sin SameSite, Firefox containers, ...

      Cross-Origin Resource Sharing, CORS
Método de protección en el cliente: Evita que código JS malicioso pueda exfiltrar
datos de un sitio web conocido. Complementa otras medidas de prevención CSRF.
Proceso
     ○ Por defecto, las peticiones asíncronas, e.g. fetch, desde JS a otros sitios no
         tienen acceso a las respuestas generadas (Same-Origin Policy)
     ○ … pero en aplicaciones basadas en JS puede ser necesario acceder a APIs
         remotas
● Basado en encabezados enviados por el servidor al navegador
       ○       El navegador pregunta (pre-fly request) al sitio si puede hacérselas
                ■   No es necesario en peticiones GET o POST si se envían encabezados o tipos básicos,
                    En otro caso es necesario también, e.g. envío de cookies, datos json, etc.
       ○       El servidor responde indicando:
                ■   orígenes que admite
                ■   métodos ( GET, POST, PUT, DELETE,...) y encabezados que aceptará
       ○       Si el servidor no acepta (sitio desconocido)→ se completa la petición pero el
               navegador no proporciona la respuesta

Content Security Policy (CSP)
●    Estándar W3C V3.0 para la prevención de ataques XSS en el cliente
      ○ El servidor indica qué contenidos son o proceden de fuentes confiables
      ○ El cliente bloquea el procesamiento de contenidos no confiables
      ○ Si se viola una regla, el cliente puede notificarlo a una url determinada
●    Las políticas son enviadas principalmente mediante encabezados o etiquetas <meta>
      ○ Como encabezados:
                 Content-Security-Policy: directiva1 valor1 valor2; …
                 Content-Security-Policy-Report-Only: ...     //recomendable solo en pruebas

     ○ En documento html
                 <meta http-equiv="Content-Security-Policy" content="directiva valor;...">

●    Ventajas:
      ○   Se puede restringir la procedencia e integridad de cualquier contenido y limitar el
          comportamiento del cliente a la hora realizar ciertas operaciones con JS
      ○ Permite mitigar o incluso eliminar el potencial efecto de XSS
      ○ Algunas directivas pueden no ser soportadas por ciertos navegadores
      ○ Debe ser un complemento frente a otras medidas adicionales descritas

Prompt Injection, un atacante incluye instrucciones para manipular el comportamiento del LLM
para eludir restricciones o extraer información sensible. CWE-1427 Improper Neutralization of Input Used for
LLM Prompting

Posibles Contramedidas
 ●     Validación y sanitización: Filtrar comandos sospechosos, límites de longitud, caracteres
       especiales. Incluye al contenido externo consultado, e.g. RAG, web…
 ●     Separación de contexto: Usar delimitadores claros entre datos del usuario e instrucciones del
       sistema
 ●     Prompts robustos: Instrucciones defensivas; definir roles/límites explícitamente; pedir al LLM
       que rechace solicitudes fuera de alcance
 ●     Modelo con guardrails o controles adicionales: Usar fine-tuning, dual-LLM para verificación
       previa, validación humana en operaciones críticas, HITL, …
 ●     Políticas de mínimo privilegio: acceso a tools, MCP, sistema de archivos, credenciales.
 ●     Aislar el alcance (sandbox): uso de contenedores/VM, subredes aisladas, filtrado de salidas…
 ●     Monitoreo y logging: Detectar patrones anómalos, auditar interacciones de alto riesgo

● La seguridad de se contempla en todo el ciclo de vida del software

      ○   Seguimiento de vulnerabilidades y actualizaciones de la cadena de suministro

      ○   Procesos de autenticación y gestión de la sesión seguros
