Tendencia actual de las arquitecturas basadas en servicios

Definiciones

  "In short, the microservice architectural style is an approach to developing a single application as a suite of
small services, each running in its own process and communicating with lightweight mechanisms, often
            an HTTP resource API. These services are built around business capabilities and independently

  of these services, which may be written in different programming languages and use different data storage

Tipos de comunicación entre
componentes
Según el instante en que emisor y receptor interactúan:
 ● Síncrono: emisor y receptor participan en el mismo instante
 ● Asíncrono: la participación es en instantes diferentes
Según la forma en que se produce la comunicación
 ● Petición/Respuesta
     ○ El cliente hace una solicitud y espera una respuesta
          (síncrona o asíncrona)
     ○ e.g. petición HTTP REST
 ● Basada en eventos
     ○ El cliente informa de un evento (mensaje) sin esperar a
          la respuesta y el receptor decide cuándo y cómo
          procesarlo
     ○ e.g. solicitud de cargo de una compra en cuenta

        Medidas para mitigar retrasos en la
        comunicación
●       Motivación:
        ¿Cómo evitar fallos en cascada del sistema (disponibilidad) debida
             a bloqueo de los nodos o retrasos en las operaciones?
 ●      Ajustar el número de conexiones máximas por nodo CWE-410
         ○ Las conexiones de un nodo consumen recursos: memoria, cpu, red
         ○ Un nodo debe rechazar "rápidamente" (fail-fast) las peticiones que no pueda atender
 ●      Reutilización de recursos costosos: conexiones (pool de conexiones), threads… CWE-1072
         ○ Reutilizar conexiones a la BD para eliminar los retrasos por establecimiento de conexión
         ○ Se pueden configurar para mantener las conexiones activas
    ●    Configuración de tiempos de espera (Timeouts) CWE-1088
          ○ Revisar valores por defecto en componentes del sistema
          ○ Adaptar timeouts en peticiones, e.g. conexiones del
             cliente, procesamiento de petición, conexiones sql,
             operaciones SQL, peticiones/respuestas REST,

 Balanceo de Carga
●     Objetivo:
       ○    Sub-sistemas para distribución de las peticiones de los "clientes" entre diferentes
            microservicios que puedan replicarse bajo demanda
 ●    Competencias:
       ○    Reparto y control de carga atendiendo a diferentes criterios:
            round-robin, número de conexiones activas, carga de los servicios (cpu,
            red…), tiempos de respuesta, ...

       ○    Posibilidad de gestionar el escalado de los servicios para atender a la
            demanda, e.g. lanzamiento y parada de servicios IaaS o PaaS, i.e.
            Elastic Load Balancer

       ○    Enrutado de peticiones a nodos en back-end, e.g. API Gateway,
            múltiples sitios diferentes, control dinámico de destinos, …

       ○    Opcionalmente, caché de elementos estáticos (servidor web):
            imágenes, JS, CSS, HTML, ... para evitar sobrecarga de componentes

Tipos de Balanceo de Carga
●    Opciones
      ○ Basados en nivel OSI: principalmente L4 (tcp, e.g. 25/smtp) o L7 (aplicación, e.g. http)
          ■ Finalización o no (pass-through) de conexiones TLS
      ○ Basados en la red, los elementos de la red determinan el destino de cada petición
              ● DNS
                  ●   Proxy ARP
            ■ Dificultad para conocer el estado real de cada nodo
      ○    Basados en servidor: las peticiones que llegan al balanceador se redirigen al servicio
           elegido
            ■   Productos independientes, e.g. nginx, haproxy, traefik,...
            ■   Servicios propios del proveedor, e.g. Amazon Elastic Load Balancer, ELB; Azure Load
                Balancer, Google Load Balancer, GLBC, Cloud Flare Load Balancing, …
      ○    Basados en cliente
            ■ El cliente consulta al balanceador a qué servicio debe realizar la petición, e.g DNS,
               Netflix Ribbon, SpringCloud load balancer, gRPC load balancing, …

     Componentes sin estado
●    Motivación
      ○ ¿Cómo puede cualquier nodo balanceado atender las
         acciones en curso de un cliente en particular?

 ●    Solución: el estado de peticiones o datos se delega a
      componentes que garantizan su persistencia
       ○    Almacenamiento compartido
       ○    Repositorios especializados NoSQL e.g. Memcached, Redis, …
       ○    Bases de Datos Relacionales o NoSQL genéricas
       ○    En el propio cliente, e.g cookies, localstorage… En este caso,
            utilizar medidas anti-modificación, e.g HMAC, JWT, …
 ●    Ventajas
       ○ Desacoplar al cliente del componente que realiza la
          operación
       ○ Facilitan la escalabilidad y la tolerancia a fallos de los
          componentes

Gestión de información en entornos
distribuidos
Motivación
  … pero, ¿cómo se garantiza la alta disponibilidad de los
servicios auxiliares: balanceador, estado, base de datos, …?

Teorema CAP (Conjetura de Brewer, 2000)
     En un sistema distribuido es imposible garantizar, a la vez, la
     Consistencia de los datos, su Disponibilidad (Availability) y
     Tolerancia a desconexiones entre nodos (Partition tolerance)
Opciones
 ●   CA, e.g única BD con un único nodo maestro, sistema de archivos compartido clásico, ...
 ●   CP, mientras los nodos no se sincronicen, la información no estará accesible
 ●   AP, la información estará eventualmente disponible, pero puede haber inconsistencias
     hasta entonces: datos obsoletos, duplicados,...
     Algunos sistemas permiten diferentes configuraciones dependiendo de las necesidades específicas

     Alta Disponibilidad en BBDD:
     uso de Cachés de Datos
Caché temporal de resultados: evitar el acceso reiterado a datos frecuentes
 ● Reducir la carga de componentes complicados de escalar, e.g. BD relacionales
 ● Evitar repetir operaciones costosas que generen un mismo contenido e.g. consultas a
    bases de datos, cálculos complejos, etc.

Tipos de Cachés
 ● En Servidor: Las BBDD permiten configurar diferentes parámetros para cachear operaciones habituales,
     e.g. caché de consultas
 ● En Cliente: en memoria local o utilizar IMDG (In-memory Data Grids) distribuidos (HA) entre diferentes
     clientes (permiten escalado horizontal)
Modos de utilización
          ○   Programático, similar a un Map, e.g. put(clave,valor), get(clave)
          ○   Integración transparente en resultados, e.g. anotaciones con JSR-107 (JCache), Spring-cache
Herramientas
      ○ Servicios de almacenamiento en memoria de clave/valor (IMDG): específicos: memcached, redis o
          genéricos: Zookeeper, Consul, Hazelcast, …
      ○ Permiten clustering para alta disponibilidad y tolerancia a fallos

Alta disponibilidad en mensajes asíncronos
Motivación
  ¿Cómo garantizar el envío de mensajes asíncronos en entornos distribuidos?
Retos
 ● Interacción entre microservicios heterogéneos
 ● Conocer ubicación dinámica de los componentes receptores (clientes)
 ● Disponibilidad de los mensajes (restricciones CAP)
Solución
 ● Utilizar capa intermedia (mesh/middleware) de comunicación asíncrona mediante mensajes
 ● Los clientes (consumidores/workers) se registran en la malla ( colas, pub/sub... )
Soluciones:
 ●   Especificaciones: AMPQ (Advanced Message Queuing Protocol), JMS (Java Message Service,
     JSR-343), MQTT, STOMP
 ●   Implementaciones (brokers): RabbitMQ, Apache MQ, Microsoft MQ, Apache Kafka...
 ●   Proveedores en la nube: AWS Simple Queue Service (SQS), Windows Azure Messaging, Google
     pub/sub, IBM WebSphere MQ, ...

Características de las mallas de
mensajes
     ●    Varían según la implementación...
           ○ Configuraciones en cluster para escalado y tolerancia a fallos (variaciones CAP)
           ○ Enrutado/Filtrado selectivo de mensajes a clientes (workers)
           ○ Elasticidad: lanzar clientes (workers) según el número de mensajes, e.g AWS SQS
     ●    Alternativas
           ○ Entrega al menos una vez. Posibles duplicados (AP)
           ○ Entrega solo una vez (CA)
                ■ Entrega transaccional. El mensaje se borra de la cola solo cuando el cliente confirma
                    la recepción
                ■ Entrega con tiempo límite. Si el cliente no confirma la recepción en tiempo límite, se
                    asignan a otro cliente
     ●    Ejemplo
           ○ AWS SQS, permite escalar dinámicamente el número de componentes dependiendo del
               número de mensajes en la cola, repetir la entrega si expira un tiempo máximo o recopilar
               mensajes no procesados (dead letters)

         Conclusiones
     ●     La arquitectura de una aplicación en la nube debe estar adaptada para hacer uso de las
           características específicas de la nube: arquitecturas distribuidas

     ●     La descomposición de una aplicación en microservicios sin estado permite su escalado
           dinámico para adaptarse a la carga del sistema o a una eventual recuperación frente a fallos
           de elementos específicos

     ●     Las arquitecturas distribuidas robustas deben tener en cuenta la carga de los nodos y los fallos
           derivados por retrasos o desconexiones temporales entre sus nodos

     ●     Los componentes elásticos deben obtener de la aplicación su configuración e información de
           estado

     ●     Un sistema distribuido debe diseñarse considerando que es imposible garantizar CAP a la
           vez: la consistencia de los datos, su disponibilidad y tolerancia a desconexiones

     ●     El balanceo de carga, el uso de cachés y los mensajes asíncronos facilitan la alta
           disponibilidad y la tolerancia a fallos
