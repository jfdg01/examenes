Consideraciones de seguridad en la Web
• Desde un punto de vista técnico la web es una aplicación
  cliente/servidor que funciona sobre Internet
• Tiene una serie de características especiales que
  sugieren herramientas de seguridad a medida:
  • Es relativamente fácil poner en marcha un servidor sin
    embargo el problema viene con las aplicaciones que se pueden
    ejecutar y sobre las que podemos tener poco control
  • Los usuarios de un servidor web no tienen porqué tener
    formación en seguridad
  • Un servidor web puede ser utilizado para entrar dentro de una
    subred y por tanto en todos los equipos de ésta
Resumen de ataques en la Web
HTTPS
• Implementación de HTTP sobre SSL/TLS para conseguir
  comunicaciones seguras cuando se accede a un servidor
  Web
• La URL empieza por https:// (puerto estándar: 443)
• Descrito en el RFC 2818
• Cuando se usa HTTPS, los siguiente elementos se
  encriptan:
 • URL del documento solicitado
 • Contenidos del documento
 • Contenidos de los formularios
 • Cookies
 • Contenidos del la cabecera HTTP
Inicio de la conexión
          Para HTTPS, el agente que
           actúa como cliente HTTP
        también actúa como cliente TLS
            El cliente inicia una conexión con el
          servidor en el puerto apropiado y luego
          envía el TLS ClientHello para comenzar
                      el handshake TLS

               Cuando el handshake TLS ha
            terminado, el cliente puede iniciar la
                  primera petición HTTP


           Todos los datos HTTP deben enviarse
              como datos de aplicación TLS
Cierre de la conexión
• Un cliente o servidor HTTP indican el cierre de la
 conexión cuando en la cabecera del mensaje actual
 incluyen la línea Connection: close
• Esta indicación de HTTP implicará que en TLS se ponga
  en acción el mecanismo de cierre seguro de la conexión
  TLS
• Otro tipo de cierre puede ser tratado como un posible
  ataque
HSTS
HTTP Strict Transport Security
• Mecanismo para indicar a los navegadores que solo pueden
  conectarse al servidor web utilizando HTTPS
• Estándar de la IETF especificado en el RFC 6797
• Funcionamiento:
  • El navegador se conecta a un sitio web por HTTP
  • El servidor responde y le indica en un campo de la respuesta HTTP:
    Strict-Transport-Security: max-age=31536000
  • A partir de este momento el navegador sabe que tiene que anteponer
    https delante de sus URLs, durante el período indicado
  • Si no se puede establecer conexión https no se realizará otra
• Problemas de seguridad
• Soluciones
  • Navegadores con especificación de sitios HSTS integrada
  • hstspreload.org
HPKP
HTTP Public Key Pinning
• Extensión de HTTP por la que se permite definir claves
  públicas del servidor para futuras conexiones como las
  que se van a usar en TLS
• Esta información se introduce en las cabeceras de
  respuesta HTTP
• Ejemplo de respuesta ante una petición HTTP:
Public-Key-Pins: max-age=2592000;
pin-sha256="E9CZ9INDbd+2eRQozYqqbQ2yXLVKB9+xcprMF+44U1g=";
pin-sha256="LPJNul+wow4m6DsqxbninhsWHlwfp0JecwQzYpOLmCQ=";
report-uri="http://example.com/pkp-report
• Problema: puede contradecir a una autoridad de
  certificación, a un certificado, …, incluso simplemente
  porque se produzca un error en su procesamiento
• Google ha dejado este mecanismo por este problema

Autenticación inicial
• La autenticación ocurre en esta capa basada en la clave
  pública/privada (Host Keys) del servidor.
• Un servidor puede tener múltiples claves de hosts
  pudiendo usar diferentes algoritmos de encriptación
  asimétrica.
• Para el proceso de autenticación el cliente debe disponer
  de la clave pública del host/servidor. Opciones:
  • El cliente tiene una base de datos local en la que se asocia
   cada host/servidor con su clave pública (fichero known_hosts)
  • El servidor y su clave se pueden asociar con un certificado, CA, …

Transport Layer Protocol
Transport Layer Protocol
Fases
• Intercambio de claves
   • Actualmente se permiten dos versiones del intercambio de claves
     Diffie-Hellman (RFC 2409)
   • Como resultado de este intercambio ambas partes comparten
     una clave maestra.
   • Además el servidor ha sido autenticado con el cliente, porque
     el servidor ha usado su clave privada para firmar su mitad del
     intercambio D-H
   • También y procedente del intercambio D-H se calcula el valor
     Hash (H) que es utilizado como identificador de sesión. Este
     no se cambiará aunque se refresquen las claves
Transport Layer Protocol
Fases
• Generación de claves
  • Se generan a partir de la clave secreta compartida K, el valor hash
    H, el identificador de sesión (suele ser H salvo que se hayan
    refrescado las claves)
Transport Layer Protocol
Fases
• Fin del intercambio de claves
  • En este momento ambas partes pueden usar las claves generadas
• Petición de servicio
  • El cliente envía un paquete donde se solicita el User Autentication
    Protocol o el Connection Protocol.
  • A partir de estos momentos los datos son intercambiados con el
    formato de mensaje antes expuesto
User Authentication Protocol
• Su función es que el cliente sea autenticado por el servidor
• Pasos:
   1.  El cliente envía un mensaje SSH_MSG_USERAUTH_REQUEST
   2.  El servidor chequea si el nombre de usuario es válido.
       1.     Si no lo es: el servidor responde con un SSH_MSG_USERAUTH_FAILURE con
              valor del campo Partial Success a False. Se detiene el proceso
       2.     Si el nombre es válido pasar al paso 3
  3.        El servidor responde con un SSH_MSG_USERAUTH_FAILURE con una
            lista de uno o más métodos de autenticación
  4.        El cliente selecciona un método de autenticación aceptable y envía
            SSH_MSG_USERAUTH_REQUEST con este método y la información
            necesaria. Se producen una serie de pasos para realizar la autenticación
  5.        Si la autenticación tiene éxito y se requieren más métodos de autenticación
            el servidor vuelve al paso 3 estableciendo el campo Partial Success a True.
            Si la autenticación falla el servidor el servidor vuelve al paso 3 con el campo
            Partial Success a False.
  6.        Cuando todos los métodos de autenticación requeridos tienen éxito el
            servidor envía un SSH_MSG_USERAUTH_SUCCESS y termina el
            protocolo
User Authentication Protocol
• Métodos disponibles
  • Publickey: típico algoritmo de autenticación utilizado en clave
    pública en la que el servidor con la clave pública del cliente (que se
    encuentra en el fichero AuthorizedKeys) envía un núnico (nonce) al
    cliente. El cliente deber responder con una firma de ese núnico
  • Password: se envía una clave encriptada por el protocolo de la
    capa de transporte.
  • Hostbased: la autenticación es realizada por el equipo del cliente,
    antes que por el usuario mismo. En este caso lo que se envía es
    una firma creada con la clave privada del equipo cliente.
Connection Protocol
• Una típica conexión segura, denominada túnel, es usada por el
  protocolo de conexión para multiplexar canales lógicos
• Mecanismo de canales
  • Para cada canal cada parte asigna un número único de canal
  • Se realiza control de flujo en los canales mediante mecanismos de
    ventana.
  • El ciclo de vida de un canal tiene tres etapas: apertura, envío de datos
    y cierre
  • …
• Tipos de canales
   • Session: para la ejecución de un programa remoto. Por ejemplo una
     Shell, un comando de sistema, …
   • x11: transporte de un flujo gráfico
   • forwarded-tcpip: para hacer port forwarding
   • direct-tcpip: para implementar port forwarding local

Recomendaciones de seguridad en la
configuración de ssh
• No permitir la conexión del usuario root
• No permitir la autenticación por contraseña (solo por clave
  pública)
• No escuchar en cualquier interfaz
• No usar nombres de usuario típicos
• Usar “allow lists” que solo permitan la conexión de ciertos
  usuarios
• Restringir también usuarios que se pueden conectar vía IP
• Utiliza software del tipo fail2ban o sshGuard para prevenir
  ataques de fuerza bruta
• Mantener el Sistema Operativo y los paquetes actualizados

SMTP (Simple Mail Transfer Protocol)
• Encapsula el mensaje de correo en un envoltorio que reenvía desde
  el origen hasta el destino a través servidores (MTAs)
• Su funcionamiento se basa en establecer una conexión TCP por el
  puerto 25
• Utiliza conexiones persistentes (se mantiene la conexión mientras se
  envían los mensajes)
• Las tres fases de la transferencia son:
   • “Acuerdo” (saludo).
   • Transferencia de mensajes.
   • Cierre.
• Como en otros protocolos la interacción entre cliente y servidor es del
  tipo comando-respuesta
  • El cliente envía comandos de tipo ASCII
  • El servidor con códigos estado frase
• Por su antigüedad tanto los bits de cabecera como los del cuerpo de
 un mensaje deben ir codificados en código ASCII de 7 bits
SMTP

     • De transporte: destinatario, remitente,…
     • Otros datos: fecha, …
  • Cuerpo (mail body): datos del mensaje de usuario

MIME
• Limitaciones del protocolo SMTP original derivadas del
 uso del código ASCII de 7 bits:
  • No se permite el envío de imágenes, ejecutables, …
• Se define en los RFCs 2045 a 2049 las extensiones
  multipropósito de correo Internet (MIME: Multipurpose
  Internet Mail Extensions)
• Estas extensiones permiten que:
  • En los mensajes se puedan enviar caracteres no ASCII
  • Se defina conjunto extensible de formatos para los mensajes
  • Los mensajes pueden estar constituidos por varias partes
   independientes, cada una con su formato
MIME
• Nuevos campos MIME en la cabecera del mensaje:
  • MIME-Version: versión MIME utilizada
  • Content-Type: formato de los datos del mensaje (imagen, audio, …)
  • Content-Transfer-Encoding: codificación utilizada para convertir los
    datos del mensaje ya que estos datos deben ser caracteres ASCII
  • Content-ID, Content-Description, …
• Así cuando llega un nuevo mensaje con estos campos
 MIME hay que:
  • Decodificarlo a sus caracteres originales a partir del valor de
    Content-Transfer-Encoding
  • En función del Content-Type realizar unas acciones u otras para
    mostrarlo en pantalla (si es imagen, audio,…)

Contra-Medidas en SP800-177 (NIST)
relacionadas con servidores y servicios
• DNSSEC: Provee autenticación e integridad a los datos DNS
  mediante la firma de éstos. Introduce para esto registros
  especiales
• DANE (DNS-based Authentication of Named Entities): Permite
  asociar certificados a nombres almacenándolos en servidores
  DNS. Se utilizará DNSSEC para enviar esta información
• SPF (Sender Policy Framework): Permite a los dueños de un
  dominio definir para un dominio, rangos de IPs de emisores
  autorizados
• DKIM (DomainKeys Identified Mail): Permite a los MTA firmar
  cabeceras y el cuerpo de un mensaje
• DMARC (Domain-based Message Authentication, Reporting,
  and Conformance): Permite a los emisores conocer la
  efectividad de sus SPF y DKIM ante ataques

Tipos de contenidos de mensaje en
S/MIME
• Los tipos definidos en el RFC 5652 son:
   • Data: es el propio tipo contenido MIME codificado
   • SignedData: usado para aplicar una firma digital a un mensaje
   • EnvelopedData: para datos encriptados
   • CompressedData: para datos comprimidos
• Clear signing:
  • Procedimiento por el que se firma un mensaje, disponiéndose el
    mensaje y la firma a continuación, sin ningún formato especial
  • Lo puede leer cualquier receptor de correo que implemente solo el
    tipo MIME.
  • La diferencia con SignedData es que el mensaje y la firma se
    encapsulan en un formato especial
Asegurando una entidad MIME
• Una entidad MIME se puede asegurar firmándola,
  encriptándola o de ambas formas
• Tras preparar una entidad MIME normal:
 • Se procesan por S/MIME
   • Firmado
   • Encriptación, …
 • A la entidad MIME se le añaden datos relacionados con seguridad,
   identificación de algoritmos y certificados y producen lo que se
   conoce como objeto PKCS
 • Este objeto se procesa como un mensaje y se vuelve a generar
   una entidad MIME, codificándola normalmente como base64
