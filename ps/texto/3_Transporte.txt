client_hello
• Versión: La versión más alta de TLS entendida por el cliente.
• Random: Una estructura aleatoria generada por el cliente que
  consiste en una marca de tiempo de 32 bits y 28 bytes
  generados por un generador de números aleatorios seguro.
  Estos valores sirven como nonces.
• SessionID: Un identificador de sesión de longitud variable.
  • Si es distinto de cero indica que el cliente desea actualizar los
    parámetros de una conexión existente o crear una nueva conexión en
    esta sesión.
  • Si es cero indica que el cliente desea establecer una nueva conexión
    en una nueva sesión.
• CipherSuite: Lista de combinaciones de algoritmos
  criptográficos soportados por el cliente, en orden
  decreciente de preferencia. Cada elemento de la lista (cada
  conjunto de cifrado) define un algoritmo de intercambio de
  claves y un CipherSpec
• Compresión: Métodos de compresión que el cliente soporta
server_hello
• Versión: contiene la versión más baja de la versión sugerida
  por el cliente y la más alta soportada por el servidor.
• Random: es generado por el servidor y es independiente del
  campo Random del cliente.
• SessionID
  • Si el del cliente no era cero, el servidor utiliza el mismo valor
  • Si era cero el campo SessionID del servidor contiene el valor para una
   nueva sesión.
• CipherSuite: contiene el conjunto de cifrado único
  seleccionado por el servidor entre los propuestos por el
  cliente.
• Compresión: contiene el método de compresión seleccionado
  por el servidor entre los propuestos por el cliente.
Parámetro CipherSuite
• El primer elemento del parámetro Ciphersuite es el método de
 intercambio de claves para el cifrado y MAC. Se soportan los
 siguientes:
  • RSA: La clave secreta se cifra con la clave pública RSA del receptor. Debe estar
    disponible un certificado de clave pública para la clave del receptor.
  • Fixed Diffie-Hellman: el certificado del servidor contiene los parámetros públicos
    Diffie-Hellman de los que se derivará las claves. El cliente enviará sus parámetros
    Diffie-Hellman en su certificado o en el mensaje Client-key-Exchange.
  • Ephemeral Diffie-Hellman: Las claves públicas Diffie-Hellman se intercambian y
    firman utilizando la clave privada RSA o DSS. Es la más segura de las opciones
    Diffie-Hellman porque da como resultado una clave temporal y autenticada.
  • Anonymous Diffie-Hellman: Cada extremo envía sus parámetros Diffie-Hellman.
    sin autenticación, por lo que es vulnerable a los ataques de hombre en el medio.
• El segundo elemento es el CipherSpec, que incluye los campos:
   • CipherAlgorithm: RC4, RC2, DES, 3DES, DES40, o IDEA
   • MACAlgorithm: MD5 o SHA-1
   • CipherType: Stream or Block
   • HashSize: 0, 16 (para MD5), o 20 (para SHA-1) bytes
   • Key Material: Una secuencia de bytes para generar claves de escritura
   • IV Tamaño: El tamaño del valor de inicialización para el cifrado CBC
server_key_exchange
• No es necesario en dos casos:
   • El servidor ha enviado un certificado con parámetros Fixed Diffie-Hellman
   • Se utiliza el intercambio de claves RSA.
• El mensaje server_key_exchange es necesario para:
   • Anonymous Diffie-Hellman: El contenido del mensaje consiste en los dos
     valores globales de Diffie-Hellman (un número primo y una raíz primitiva de
     ese número) más la clave pública Diffie-Hellman del servidor.
   • Ephemeral Diffie-Hellman: El contenido del mensaje incluye los tres
     parámetros anteriores más una firma de esos parámetros.
   • Intercambio de claves RSA (en el que el servidor utiliza RSA pero tiene una
     clave RSA sólo de firma): Por consiguiente, el cliente no puede enviar una
     clave secreta cifrada con la clave pública del servidor. En su lugar, el servidor
     debe crear un par de claves públicas/privadas RSA temporales y utilizar el
     mensaje server_key_exchange para enviar la clave pública. El contenido
     del mensaje incluye los dos parámetros de la clave pública RSA temporal
     (exponente y módulo) más una firma de esos parámetros.
certificate_request
• A continuación, un servidor no anónimo (servidor que no utiliza Diffie-
  Hellman anónimo) puede solicitar un certificado al cliente.
• El mensaje certificate_request incluye dos parámetros:
  tipo_de_certificado y autoridades_de_certificado
  (aceptables).
• El tipo de certificado indica el algoritmo de clave pública y su uso:
  • RSA, firma sólo
  • DSS, firma sólo
  • RSA para Diffie-Hellman fijo; en este caso la firma se utiliza sólo para la
    autenticación del certificado, enviando un certificado firmado con RSA
  • DSS para Diffie-Hellman fijo; de nuevo, se utiliza sólo para la autenticación.
• Después se envía el mensaje server_done, que es obligatorio para
  indicar el final del saludo del servidor y los mensajes asociados.
• Si el servidor ha solicitado un certificado, el cliente comienza esta
  fase enviando un mensaje de certificado. Si no hay ningún certificado
  adecuado disponible, el cliente envía una alerta de
  no_certificado en su lugar.
client_key_exchange
• El contenido del mensaje depende del tipo de intercambio
 de claves
 • RSA: El cliente genera una clave pre-master de 48 bytes y encripta
   con la clave pública desde el certificado del servidor o la clave RSA
   temporal desde un mensaje server_key_exchange. Su uso
   para calcular un secreto maestro se explica más adelante.
 • Diffie-Hellman efímero o anónimo: Se envían los parámetros

 • Fixed Diffie-Hellman: Si los parámetros públicos de Diffie-Hellman
   del cliente se enviaron en un mensaje de certificado, el contenido
   de este mensaje es nulo.
certificate_verify
• Verificación explícita de un certificado de cliente.
• Este mensaje sólo se envía después de cualquier
  certificado de cliente que tenga capacidad de firma
  (es decir, todos los certificados excepto los que contienen
  parámetros Diffie-Hellman fijos).
• Se firma (con la clave privada del certificado) un código
  hash basado en los mensajes anteriores,
 CertificateVerify.signature.hash(handshake_messages);
• handshake_messages se refiere a todos los mensajes
 del protocolo Handshake enviados o recibidos a partir de
 client_hello pero sin incluir este mensaje.
 change_cipher_spec
 finished_message
• Este mensaje se envía utilizando el protocolo
  ChangeCipherSpec.
• El mensaje final verifica que el intercambio de claves y los
  procesos de autenticación se han realizado correctamente.
  El contenido de finished_message es:

PRF(master_secret, finished_label, MD5(handshake_messages)||SHA(handshake_messages))

  finished_message.

• La mayoría de claves y parámetros utilizados para

 • Una clave maestra compartida
 • Los parámetros criptográficos (key_block) a obtener partir de esta

   • Client write MAC secret
   • Server write MAC secret
   • Client write key
   • Server write key
   • Client write IV
   • Server write IV

Obtención de la clave maestra
• Tiene 48 bytes y es única para la sesión
• Se crea en dos fases.
  • Primero se intercambia una pre_clave_maestra. Dos opciones:
    • RSA: Se genera por el cliente, se encripta con la clave pública RSA
      del servidor y se envía al servidor.
    • Diffie-Hellman: Tanto el cliente como el servidor generan una clave
      pública Diffie-Hellman. Una vez intercambiados, cada bando realiza el
      cálculo Diffie-Hellman para crear el pre_master_secret compartido.
  • Después, ambas partes generan la clave_maestra
key_block




• A partir de aquí podemos obtener:
  • Client write MAC secret
  • Server write MAC secret
  • Client write key
  • Server write key
  • Client write IV
  • Server write IV
Suite de cifrado
• Establecimiento tras Handshake
  • KeyExchangeMethod: RSA, Diffie-Hellman
  • CipherAlgorithm: RC4, RC2, DES, 3DES, DES40, or IDEA
  • MACAlgorithm: MD5 or SHA-1
  • CipherType: Stream or Block
  • HashSize: 0, 16 (for MD5), or 20 (for SHA-1) bytes
  • Key Material: A sequence of bytes that contain data used in
    generating the write keys
  • IV Size: The size of the Initialization Value for Cipher Block
    Chaining (CBC) encryption

Renegociación
• Durante una conexión TLS se puede solicitar una
  renegociación de los parámetros de seguridad
• Esto implica una nueva ejecución del protocolo Handshake
• La renegociación puede ser iniciada por cliente o servidor:
  • El cliente enviara un típico mensaje ClientHello
  • El servidor enviaría un mensaje HelloRequest (perteneciente al
   protocolo Handshake)
• Escenarios para solicitar renegociación
  • Solicitar el certificado del cliente a partir de un momento determinado
  • Incrementar la seguridad cuando se navega por una determinada
    zona de un sitio web
  • Ocultar información de la suite de cifrado a utilizar. El establecimiento
    de la nueva suite de cifrado ya se realizará bajo encriptación

Cierre de la conexión
• Se emiten paquetes especiales para cerrar la conexión.
• El objetivo es evitar un “truncation attack”, o un cierre de
  la conexión no autorizado, utilizando TCP
• El interlocutor que quiere cortar la conexión emite una
  alerta close_notify
• El otro interlocutor al recibir este paquete descarta
 cualquier envío y emite así mismo un close_notify

Problemas en TLS v1.2
• Demasiados pasos (RTTs) en el protocolo Handshake
• Demasiados CipherSuites, decenas de combinaciones
  que dificultan la elección de las mejores
• Elección de parámetros para ciertos algoritmos en
  manos de usuarios que configuran servidores
• Algunas partes del protocolo no se incluyen en la firma
  digital que genera el servidor con su clave privada. Esto
  deja la puerta abierta a ataques “downgrade” que
  permiten establecer cifrados débiles
TLS v1.3
• Publicado en agosto 2018
• El objetivo es aumentar la seguridad y la eficiencia
• Con respecto al protocolo Handshake de TLS v1.2
  • Se prohíbe el uso de intercambio de claves RSA y otros elementos
    considerados pocos seguros (los veremos más adelante).
  • Se elimina el uso del protocolo ChangeCipherSpec.
  • Se eliminan los mensajes sever_key_Exchange y
    client_key_Exchange. Adjunto al mensaje Hello (de cliente o
    servidor) se envían los parámetros necesarios para la compartición
    de clave (KeyShare Extensions)
  • Se introducen EncryptedExtensions: extensiones del mensaje
    server_hello que deben cifrarse
  • De hecho cada mensaje enviado después de server_hello se
    cifra -> Se adelanta el cifrado de la conexión
TLS v1.3
• Se reduce al máximo la negociación al elegir
 individualmente cada elemente

Otras eliminaciones en TLS v1.2
• Se eliminan elementos inseguros y se reducen (se
 simplifican) opciones para aumentar la seguridad:
 • Cifrados autenticados CBC-then-MAC
 • Algoritmos básicos como RC4, SHA1, MD5
 • Compresión
 • Renegociación
 • Ciertos nonces (por ejemplo aquellos que incluyen un timestamp
   de 32 bits)
• En cualquier caso también se van a añadiendo otros
 algoritmos y elementos que aumentan la seguridad:
 • Protección ante Downgrade
 • Algoritmos criptográficos más seguros, …
Encriptación autenticada
• Opciones:
  • Primero autenticación, luego encriptación
     • Usado hasta ahora en SSL/TLS
     1. T = MAC(K1 , M )
     2. E(K2 , [M || T ])
  • Primero encriptación, luego autenticación
     • Usado en IPSec
     1. C = E(K2 , M ).
     2. T = MAC(K1 , C )
     3. Se envía (C, T)
  • Encriptar y autenticar paralelamente
     • Usado en SSH
     • C = E(K2 , M ).
     • T = MAC(K1 , M )
     • Se envía (C, T)
  • En TLS v1.3 se proponen usar algoritmos basados en las dos últimas opciones
    como GCM, CCM o ChaCha20-Poly1305.
  • Authenticated Encryption with Associated Data (AEAD): término para indicar
    que no solo se realiza la autenticación de los datos del paquete de datos a enviar
    sino que también se autentican datos adicionales (Associated Data) como por
    ejemplo, longitudes de paquetes, números de secuencia, …
